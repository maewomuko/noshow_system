## 1. 專案背景與目標

本專案為「門診預約管理與未到診風險分析系統」。
使用 106,982 筆真實門診資料，建立一套結合資料結構、預約管理與未到診風險分析的系統。
專案分成兩個主要部分：

1. 門診預約管理系統
   * 使用 BST、Max-Heap、Doubly Linked List、Queue，以及病患索引 PatientBST。
   * 透過 Streamlit 建立互動式管理介面。
   * 支援預約查詢、風險排序、確認到診（`confirm_attend`）、取消預約、候補遞補、新增預約，以及超額預約估計（`expected_noshow`，用 `build_calibration()` 把分數換成同分者的歷史實際未到率再加總）。
2. 資料結構效能實驗
   * 比較不同資料結構在搜尋、插入、刪除、Top-K 及 Queue 操作上的差異。
   * 使用實驗 CSV（`experiments/results_exp1~3.csv`）呈現比較次數、資料搬移次數、執行時間及實際重複次數。
   * 分析理論時間複雜度與實際執行效能之間的差異。

開發過程必須以現有專案程式碼、資料與實驗結果為依據，不得自行假設尚未實作的功能。

## 3. 開發與程式碼修改原則

### 3.1 保留既有功能

* 不得為了改善外觀而破壞原本功能。
* 不得任意更換核心資料結構。
* 不得在未理解程式依賴關係前重構核心模組。
* 修改前先說明修改目的、影響範圍與可能風險。
* 優先採取局部修改，避免不必要的大規模重寫。

### 3.2 資料結構一致性

所有結構共用同一份 `Record` 物件，必須維持彼此一致：

* **cancel 的順序**：BST 節點的 `ll_node` 存著 Linked List 節點位置。必須先用 `bst.search` 找到節點 → `roster.delete_node(node.ll_node)` → `bst.delete` → `heap.remove` → `patients.remove_record`。不可先刪 BST，否則會失去 `ll_node`，Linked List 就只能 O(n) 搜尋刪除。
* **add／refill 的順序**：`node = roster.append(record)` → `bst.insert(record, node)` → `heap.push(record)` → `patients.insert(record)`。
* **Heap 的 `pos` 字典**：`MaxHeap.pos` 記錄 `appointment_id → 陣列索引`，`update_key`／`remove` 才能 O(log n)。任何交換元素的操作都要經過 `_swap` 同步更新 `pos`。
* `update_key` 會直接修改共用 Record 的 `risk`；同一個 Record 不要同時放進兩個 MaxHeap 又各自 `update_key`。
* 新增、取消、確認到診與候補遞補後，都要以 `check_consistency()` 驗證（測試中必須呼叫）。

不得為了簡化程式而破壞上述依賴關係。

### 3.3 原始資料與 Log 保護

* `data/healthcare_noshows.csv` 為唯讀資料，不得修改或覆寫。
* Log 採追加方式（`open(..., "a")` + `flush()` + `os.fsync()`），不得擅自清除。
* `data/logs/` 被 `.gitignore` 排除，刪除後無法從 git 還原。未取得使用者同意前，不得刪除 log、測試紀錄或實驗結果。
* 如果需要重置測試環境，必須先說明影響範圍並取得同意。

### 3.4 Streamlit Session State

* `AppointmentSystem` 存在 `st.session_state.system`（`app/common.py` 的 `get_system()`），頁面只呼叫 `AppointmentSystem` 的方法。
* 確保新增、取消與確認到診等操作能持續生效，避免使用者操作後資料又恢復成初始狀態。
* 效能分析頁只讀實驗 CSV，不使用 session_state 裡的系統。

## 4. Streamlit 介面設計規範

### 4.1 整體風格

採用 Hybrid 混合式設計：

* 醫療管理儀表板：清楚、直覺、容易操作。
* 技術分析介面：呈現資料結構、演算法與效能資訊。

### 4.2 六個頁面（`app/Home.py` + `app/pages/` 五頁）

1. 首頁 Home：選日期／區域、當日預約總覽、風險燈號統計、風險分數驗證（全部歷史資料）。
2. 預約查詢：BST 搜尋、線性搜尋比較次數與耗時、BST 搜尋路徑圖。
3. 風險關懷名單：Max-Heap `top_k` 高風險名單、確認到診／取消、Heap 前 4 層結構圖。
4. 候補與超額預約：`expected_noshow` 預估空位、LinkedQueue 候補隊伍（先進先出）與遞補操作。
5. 新增預約：風險評分、病患歷史（PatientBST）、資料結構插入。
6. 效能分析：讀取實驗 CSV，呈現三組效能實驗。

不得將資料結構視覺化做成純裝飾：

* BST 應呈現真實搜尋路徑或實際節點資料。
* Heap 應呈現真實 Heap 結構，依系統限制顯示適當層數（目前 `heap_preview(4)`）。
* Queue 應呈現真實先進先出順序。
* 效能圖表必須對應實際實驗結果。

## 5. 資料與實驗分析規範

所有數據必須能追溯至原始資料、程式碼或實驗 CSV。必須區分：

* 理論時間複雜度。
* 實際執行時間（`avg_ms`）。
* 比較次數（`avg_comparisons`）。
* 資料搬移次數（`avg_moves`）。
* 實驗環境與測量條件。

測量條件注意事項：

* 實驗每組**最多** 1000 次、限時 3 秒、至少 5 次（`experiments/common.py` 的 `MAX_RUNS`／`TIME_BUDGET_S`／`MIN_RUNS`）。慢的組合會提早停止，實際次數記在 CSV 的 `runs` 欄。引用數據時要一併註明 `runs`，不可一律寫「跑 1000 次取平均」。
* CSV 沒有記錄硬體與 Python 版本。若需呈現實驗環境，向使用者詢問或改程式記錄；沒有來源時標示「未記錄」，不得自行填寫。
* README「實測數字」（`demo_core.py` 單次測量）與「實驗結果摘要」（CSV 平均值）是不同測量，引用時要註明來源。

其他原則：

* 不得只用執行時間判斷資料結構優劣。
* 不得將規則式風險評分描述為機器學習模型；分數用來排序，不等於機率。
* 不得將相關性直接解釋為因果關係（例如簡訊與未到率）。
* 不得隱藏不符合預期的實驗結果（例如 K 接近 n 時 `sorted()` 比 heap `top_k` 快）。
* 不得自行編造效能數據。
* 如果程式碼、CSV 與簡報數據不一致，必須先找出差異並向使用者說明。

## 6. 簡報設計規範

### 6.1 整體視覺方向

簡報採用 Tech 科技研究風格。

* 比例：16:9。
* 背景：深藍色科技風格（背景與卡片）。
* 主色（強調色）：青綠色。
* 文字：高對比度，確保投影時容易閱讀。
* 風險顏色：紅、黃、綠，綠燈必須是明顯的綠色，不可與主色青綠混淆。

建議配色：

* 背景：#101C2C
* 卡片：#1B2D43
* 主色：#36B6AC
* 主要文字：#E8EDF4
* 次要文字：#8FA8C4（在卡片上對比約 5.7:1；原 #6584A5 僅約 3.6:1，投影小字看不清）
* 高風險：#D94B4B
* 中風險：#D9A441
* 低風險：#3FA35B

### 6.2 敘事方式

採用 Problem-driven 問題導向敘事：
問題背景 → 解決方案 → 系統架構 → 資料結構 → 效能實驗 → 實驗結果 → 結論。

簡報不能只是將程式功能逐頁列出，而是要說明：

* 為什麼需要這個系統？
* 原本的管理方式有什麼問題？
* 為什麼選擇這些資料結構？
* 不同資料結構實際帶來什麼差異？
* 實驗結果如何支持設計選擇？

### 6.3 技術內容呈現

* 優先使用架構圖、流程圖、資料結構示意圖及實驗圖表。
* 不要將大量程式碼直接放進簡報。
* 不要用沒有實際意義的裝飾圖代替技術內容。
* 圖表必須使用真實實驗資料。
* 理論複雜度與實際測量結果必須分開說明。
* 簡報內容必須與實際程式碼一致。

## 7. Canva 簡報製作與事前預覽流程

### 7.1 Canva 連線檢查

當使用者要求製作或重新設計簡報時，若 Canva 整合工具可用，應優先使用 Canva。開始製作之前：

1. 檢查是否已連接 Canva。
2. 確認目前連線是否支援建立及編輯簡報。
3. 如果 Canva 無法使用，向使用者說明缺少的連線或功能，並暫停 Canva 製作。
4. 不得假裝已經成功建立或儲存 Canva 設計。
5. 如果 Canva 已經連接且可以使用，不得要求使用者重複連接。

### 7.2 正式製作前的設計預覽（強制）

在製作完整簡報之前，必須先提供視覺設計預覽，包含：

* 整體視覺風格與設計理念。
* 配色方案與字體方向。
* 投影片版面配置與資訊層級。
* 每一頁投影片的初步內容規劃。
* 具有代表性的投影片視覺預覽。

至少提供以下四種投影片預覽：

1. 封面：專題名稱、副標題、專案識別與整體視覺配置。
2. 問題與背景：如何引出問題，以及如何呈現問題的重要性。
3. 技術架構：系統架構與資料結構之間的關係。
4. 實驗結果：如何呈現效能數據、圖表與比較結果。

只要工具支援，就應優先提供實際視覺預覽（投影片縮圖、版面示意圖或設計樣板），而不是只提供文字描述。
如果無法產生實際視覺預覽，必須提供足夠詳細的版面草圖，並向使用者說明限制。

### 7.3 使用者確認機制

完成預覽後，必須停止製作流程，等待使用者提供意見。在使用者確認之前：

* 不得直接製作完整 Canva 簡報。
* 允許使用者要求修改配色、字體、版面、圖表、資訊密度或整體視覺風格。
* 根據使用者意見修改預覽。
* 只有在使用者明確同意後，才能進入完整簡報製作階段。

使用者同意整體設計方向，不代表允許自行修改與設計無關的專案內容。

### 7.4 正式製作完整簡報

取得使用者同意後：

1. 使用 Canva，依照已確認的視覺風格建立簡報。
2. 按照已確認的投影片大綱與內容順序進行製作。
3. 統一字體、間距、配色與資訊層級。
4. 優先使用能有效傳達資訊的圖表、架構圖、流程圖及技術示意圖。
5. 避免過度裝飾、重複使用相同卡片版型，以及塞入過多文字。
6. 如果 Canva 整合工具支援，應盡可能保留投影片的可編輯性。

### 7.5 Canva 製作後檢查

完成後必須：

* 確認投影片順序與敘事邏輯是否連貫。
* 確認文字是否容易閱讀，以及整體視覺風格是否一致。
* 根據原始實驗 CSV 重新核對所有圖表（含 `runs`）。
* 確認技術架構圖是否正確反映實際程式實作。
* 找出遺漏內容、缺乏依據的說法，以及版面配置問題。
* 如果 Canva 成功建立簡報，提供使用者 Canva 簡報連結。

如果 Canva 製作失敗，或只完成部分內容，必須如實說明，不得宣稱已經全部完成。

## 8. 測試與驗收

每次修改程式後，依照修改範圍執行適當測試（至少 `python -m pytest tests -q`）。至少確認：

* 原有功能沒有遭到破壞。
* 新增、取消、確認到診及候補遞補操作正常。
* 各資料結構保持一致（`check_consistency()`）。
* Session State 能正確保留系統狀態。
* 實驗 CSV 能正常讀取。
* 圖表呈現的數據與來源一致。
* 自動化測試結果已確認。

如果測試失敗，必須說明失敗項目、原因與影響，不得宣稱全部通過。

## 9. Claude Code 執行流程

每次接到開發或設計任務，依照以下流程執行。
**小改動例外**：只改單一檔案、不動 `core/` 與資料結構、不涉及簡報（例如修文字、改註解、調整頁面排版），可以跳過第三階段直接執行，但仍要驗證與回報。

第一階段：理解

* 閱讀相關程式碼與專案文件。
* 確認使用者要求與現有功能的關係。
* 找出可能受到影響的模組。

第二階段：分析

* 說明目前實作狀況。
* 列出需要修改的檔案。
* 說明修改目的、預期結果與風險。

第三階段：提出計畫

* 提供具體修改方案。
* 如果涉及大幅重構，先取得使用者同意。
* 如果涉及簡報製作，必須先完成 Canva 設計預覽與確認流程。

第四階段：執行

* 按照確認後的方案進行修改。
* 優先局部修改。
* 保留既有功能與資料。

第五階段：驗證

* 執行必要測試。
* 檢查資料一致性。
* 核對實驗數據與視覺呈現。

第六階段：回報，清楚列出：

* 修改了哪些內容與檔案。
* 新增了哪些功能。
* 執行了哪些測試。
* 是否有尚未解決的問題。
* 如果建立 Canva 簡報，提供實際可用的 Canva 連結。
